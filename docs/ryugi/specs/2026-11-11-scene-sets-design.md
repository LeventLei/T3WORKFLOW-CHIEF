# 设计说明：多套场景配置，按项目选用

日期：2026-11-11　状态：待用户确认　前一版：`2026-11-10-scenes-config-design.md`

## 为什么改

现在全局只有一套场景，所有项目共用。用户除了写代码，还在别的项目里做视频，那边要派的 Worker 是编剧、导演、原画，和摸底、开发、审查这套完全不同。两类场景放在一套里，Chief 挑场景时容易混用，规则（必须审查、失败升级）也只适合开发。

成功的样子：

- 面板里可以有好几套场景配置，比如“开发”“视频”；
- 每个 T3 项目选用其中一套，没选的用默认那套；
- Chief 在某个项目里只看这个项目那一套的场景和规则，不会把编剧派到代码项目，反过来也一样。

上一版设计里的第 7 条决定（只保留一套全局配置）和“不做”里的“不做多套配置 / 按项目覆盖”，由本说明取代。

## 已定下的决定（用户 2026-11-11 在对话中确认）

1. 场景配置可以有多套，每套有自己的显示名，例如“开发”“视频”。
2. 每套内部就是现在的场景配置：每个场景有首选、备选、兜底三个模型，场景可以新增、删除、改名。
3. 每个项目绑定一套配置，Chief 在该项目里只从这一套挑选、组合场景。
4. 没绑定的项目用默认的那一套。
5. 规则跟着每一套走。原因：“写代码默认用哪个场景”“失败后转给哪个场景”这类规则指向的是本套里的场景，几套之间没法共用。（**我的决定**）

## 配置格式 v3

**我的决定**：仍然只用一个文件 `~/.chief-t3/config.json`（`CHIEF_CONFIG` 可覆盖路径）。几套配置和项目绑定都写在这个文件里。这样做有三个好处：

- 一次保存就是一次原子写入，冲突检测（baseMtime）和备份逻辑不用改；
- Chief 只需要读一个文件；
- 项目绑定和配置套放在一起，删一套配置时可以同时清理绑定。

```json
{
  "schemaVersion": 3,
  "defaultSet": "dev",
  "sets": {
    "dev": {
      "label": "开发",
      "scenes": { "fast-dev": { "label": "小改动", "when": "…", "delegateRole": "implementation", "access": "write", "primary": { "provider": "…", "model": "…" }, "backup": null, "fallback": null } },
      "rules": { "requireReview": true, "defaultWriteScene": "fast-dev", "escalateTo": "dev", "escalateAfter": 2, "maxParallelWriters": 8, "maxReworkRounds": 3, "contractFileThreshold": 2 }
    },
    "video": {
      "label": "视频",
      "scenes": { "writer": { "label": "编剧", "when": "…", "delegateRole": "general", "access": "write", "primary": { "…": "…" } } },
      "rules": { "requireReview": false, "maxParallelWriters": 2, "maxReworkRounds": 2, "contractFileThreshold": 2 }
    }
  },
  "projects": {
    "/Users/me/Desktop/Forma": "dev",
    "/Users/me/知识库": "video"
  }
}
```

**字段：**

- `sets`：至少一套。
  - 套的键名规则和场景键名相同：小写字母、数字、连字符。新建时由显示名自动生成，用户可以改。
  - `label` 必填。
  - `scenes`、`rules` 的结构和校验与 v2 完全相同，只是每套各算各的。
- `defaultSet`：必填，必须是已有的一套。
- `projects`：可选。
  - 键是 T3 项目工作区根目录的绝对路径，去掉末尾的斜杠。
  - 值是套的键名。
  - 不写的项目使用 `defaultSet`。

**校验**（`scripts/validate-workflow.mjs` 改写为 v3，仍然零依赖，浏览器和命令行都能用）：

- 每套内部沿用 v2 的全部规则，报错路径带上套名，例如 `sets.video.scenes.writer.primary.model`。其中两条本来就是有条件的，所以视频这类套可以没有审查场景：
  - 只有 `requireReview` 为 true 时，才要求本套有 review 场景；
  - 审查场景的首选模型不能与实现场景的首选模型相同。
- `defaultSet` 和 `projects` 的每个值都必须指向存在的套。
- `projects` 的键必须是绝对路径。
- `schemaVersion` 为 1 或 2 时报“这是旧格式，请先运行转换”。
- `workflow.schema.json` 同步改成 v3。

## Chief 怎么用（SKILL.md 和 AGENTS.md 区块）

1. **确定项目根目录**：用当前 T3 项目的工作区根目录。如果线程在 T3 创建的 worktree 里，用它所属项目的根目录，不用 worktree 路径。
2. **选套**：在 `projects` 里找这个路径。
   - 找不到时，再找一个是它上级目录的键，取最长的那个。
   - 都没有就用 `defaultSet`。
3. **首次汇报**：写明用的是哪个配置文件、哪一套，以及是项目绑定的还是默认的。
4. **使用范围**：之后所有挑场景、默认写代码场景、失败升级、模型顺延和审查规则，都只看这一套的 `scenes` 和 `rules`。规则本身与 v2 相同。
5. **不跨套借用**：不得使用其它套里的场景。本套里没有合适的场景时，说明情况并请用户决定。
6. **配置无效**：报告具体问题、停止派单，处理方式不变。

`~/.t3-tasks/<project>/` 台账规则不变。

## 面板

**布局：** 回到“左栏 + 主区”，沿用上一版移除前的左栏样式、移动端抽屉和动效。

**左栏：**

- “场景配置”组：列出所有套，每项显示名称和绑定的项目数。默认那套带“默认”徽标。底部有“新建”。
- “项目”入口：点击后主区显示项目分配页。

**主区（选中某一套时）：**

- 标题行：套的显示名（可以直接改），右侧更多菜单里有：
  - 复制一份；
  - 设为默认；
  - 删除：默认那套不能删；删除时如果有项目绑定，二次确认里列出这些项目，确认后它们改用默认那套。
- 下面是现在的“场景”“规则”“高级”三块，内容和交互不变，作用于这一套。
- **新建**提供两种起点：空白（含一个空场景，审查开关关闭）和“复制当前这套”。

**项目分配页：**

- 列出 T3 项目：只读，白名单只取 `title`、`workspace_root`、`archived_at`；已归档的放在折叠区。
- 每行一个下拉，选项是“跟随默认（当前：开发）”和各套名称。

**保存：**

- 顶栏只有一个保存 / 撤销修改，作用于整个文件，包括所有套和项目绑定；保存条的改动计数、校验问题定位都保持现状。
- 切换左栏选中项不丢失未保存的修改。

**服务端：**

- `GET/PUT /api/config` 和 `GET /api/providers` 保持不变，读写的是 v3 全文件。
- `GET /api/projects` 是新增的，只返回上面的白名单字段。读 T3 数据库的方式恢复 v1 的 `readT3Projects`：只读，Node 自带的 sqlite 或 `sqlite3 -readonly`。
- 读到 v2 文件时，服务端在内存里转成 v3 返回，并带上 `upgradedFrom: 2`；页面提示“保存后会转换为新格式”，保存时写 v3 并备份旧文件。
- `/api/state` 不变。
- 不读 `~/.t3/userdata/secrets`；T3 数据库只读。

## 转换

`scripts/migrate-to-scenes.mjs` 扩展到可以输出 v3：

- **输入 v1：** 先按原规则转成 v2，再按下面的 v2 规则处理。
- **输入 v2：** 包成 `sets.dev`（显示名“开发”），`defaultSet: "dev"`，`projects: {}`。
- **输入 v3：** 校验后原样使用。
- **`--apply`：** 写出 `~/.chief-t3/config.json`，已存在就先备份。上一版迁移留下的 `~/.t3-tasks/*/workflow.json.bak.*` 不动，也不自动导入。
- **出厂默认：** 仓库里的 `skills/chief-t3/workflows/default.json` 转成 v3，只有“开发”一套。**我的决定**：不内置“视频”套，用户在面板里新建并选模型。

## 其它文件

- `AGENTS.md` 的 chief-t3 区块、`README.md` 的配置说明和面板小节，按上面改写。

## 不做

- 不在一套里引用另一套的场景，也不做继承或覆盖。
- 不在面板里新建 T3 项目，也不改 T3 数据。
- 不内置视频场景的具体内容。

## 验收

- **语法和校验：**
  - `node --check` 两个 mjs，以及面板模块脚本的语法检查；
  - `node scripts/validate-workflow.mjs skills/chief-t3/workflows/default.json` 通过；
  - v2 文件报“旧格式”。
- **坏例子：** 以下每个都要报出对应错误：
  - `defaultSet` 指向不存在的套；
  - 项目绑定指向不存在的套；
  - 某一套的审查首选与实现首选相同，报错路径带套名；
  - 一套 `requireReview: false` 且没有审查场景，校验能通过。
- **面板：** 用 `CHIEF_CONFIG=<临时文件>` 起测试服务，在测试端口走一遍：
  - 读到 v2 时提示转换；
  - 新建一套空白配置“视频”，加场景、选模型；
  - 把一个项目绑到“视频”；
  - 保存后刷新，读回一致；
  - 删除“视频”，确认后该项目回到默认；
  - 默认那套不能删。
- **迁移：** 在临时 HOME 上跑 `--apply`，分别用 v1、v2、v3 输入。真实迁移在用户确认后由主线程执行。
